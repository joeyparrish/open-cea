# SMPTE ST 334-2:2015 — Caption Distribution Packet (CDP) digest

Digest of SMPTE ST 334-2:2015, "Caption Distribution Packet (CDP)
Definition" (revision of 334-2-2007). The CDP was originally section 11
of CEA-708-B; CEA transferred it to SMPTE. Section numbers in
parentheses refer to the standard. The PDF (`st0334-2-2015.pdf`) is
gitignored; this digest is written to be sufficient for the encoder.

Scope note: 334-2 defines only the CDP byte structure. The surrounding
ANC packet (DID / SDID / data count / checksum) is SMPTE ST 291-1 and
ST 334-1 (digested in [`334-1.md`](./334-1.md)).

## 1. Conventions (section 5)

* Syntax elements are listed MSB-first within each byte; multi-byte
  numeric fields are most-significant byte first ("uimsbf", as in
  CEA-708). This is the reverse of SDI wire order, which is irrelevant
  for MCC hex.
* "shall" is mandatory, "should" recommended, "may" optional.
  "Reserved" bits have a fixed value given in the tables and must be
  sent as that value.

## 2. Overall structure (section 5.1, Table 1)

```
cdp() {
  cdp_header()           required, 7 bytes
  time_code_section()    optional, 5 bytes
  ccdata_section()       optional (should normally be present), 2 + 3*cc_count bytes
  ccsvcinfo_section()    optional, 2 + 7*svc_count bytes
  [future_section()...]  optional, ids 0x75..0xEF, placed just before the footer
  cdp_footer()           required, 4 bytes
}
```

* Exactly one header and one footer. At most one of each optional
  section. Sections appear in the order above.
* Receivers skip unknown sections using their length byte (5.7).

## 3. cdp_header (section 5.2, Table 2) — 7 bytes

| Byte | Bits | Field |
|------|------|-------|
| 0–1  | 16   | `cdp_identifier` = 0x9669 |
| 2    | 8    | `cdp_length`: byte count of the whole CDP, from the first identifier byte through `packet_checksum` inclusive |
| 3    | 7..4 | `cdp_frame_rate` (Table 3) |
| 3    | 3..0 | reserved, `1111` |
| 4    | 7    | `time_code_present` |
| 4    | 6    | `ccdata_present` |
| 4    | 5    | `svcinfo_present` |
| 4    | 4    | `svc_info_start` |
| 4    | 3    | `svc_info_change` |
| 4    | 2    | `svc_info_complete` |
| 4    | 1    | `caption_service_active` |
| 4    | 0    | reserved, `1` |
| 5–6  | 16   | `cdp_hdr_sequence_cntr` |

Flag semantics:

* `time_code_present`, `ccdata_present`, `svcinfo_present`: 1 if and
  only if the corresponding section is in this CDP.
* `svc_info_start` / `svc_info_change` / `svc_info_complete`: must be 0
  when the CDP has no ccsvcinfo_section; otherwise must equal the
  copies inside that section (see section 6 below).
* `caption_service_active` (the prose calls it `caption_active`): 1
  when the CDP *stream* is conveying an active caption service, 0 when
  it is not. This is a stream-level statement, not "this CDP carries a
  service block". The standard does not restrict "caption service" to
  DTVCC; the ccsvcinfo section treats the line-21 (608) service as
  caption service number 0, so a stream carrying active 608 captions
  is conveying an active caption service.
* `cdp_hdr_sequence_cntr`: previous CDP's value + 1, wrapping
  65535 -> 0. The first CDP of a sequence may use any value. A jump
  signals a stream switch or error to receivers (4.4, 5.5.1).

### Table 3 — frame-rate codes and per-frame budgets (normative)

"cc_count" and the byte counts are what *shall* be carried in every
CDP at that rate. Byte counts are cc_data_1/cc_data_2 payload bytes
(2 per tuple), so tuples = bytes / 2.

| Code   | Rate            | cc_count | 608 bytes (tuples) | 708 bytes (tuples) |
|--------|-----------------|----------|--------------------|--------------------|
| `0000` | forbidden       |          |                    |                    |
| `0001` | 24000/1001      | 25       | 4/6 (2/3)          | 46/44 (23/22)      |
| `0010` | 24              | 25       | 4/6 (2/3)          | 46/44 (23/22)      |
| `0011` | 25              | 24       | 4 (2)              | 44 (22)            |
| `0100` | 30000/1001      | 20       | 4 (2)              | 36 (18)            |
| `0101` | 30              | 20       | 4 (2)              | 36 (18)            |
| `0110` | 50              | 12       | 2 (1)              | 22 (11)            |
| `0111` | 60000/1001      | 10       | 2 (1)              | 18 (9)             |
| `1000` | 60              | 10       | 2 (1)              | 18 (9)             |
| `1001`..`1111` | reserved |         |                    |                    |

At 24 / 23.976 the 608 allocation alternates between 2 and 3 tuples
(and 708 between 23 and 22) frame to frame. Rates differing by 0.1%
share a budget (4.1).

## 4. time_code_section (section 5.3, Table 4) — 5 bytes, optional

| Byte | Bits | Field |
|------|------|-------|
| 0    | 8    | `time_code_section_id` = 0x71 |
| 1    | 7..6 | reserved `11` |
| 1    | 5..4 | `tc_10hrs` |
| 1    | 3..0 | `tc_1hrs` |
| 2    | 7    | reserved `1` |
| 2    | 6..4 | `tc_10min` |
| 2    | 3..0 | `tc_1min` |
| 3    | 7    | `tc_field_flag` |
| 3    | 6..4 | `tc_10sec` |
| 3    | 3..0 | `tc_1sec` |
| 4    | 7    | `drop_frame_flag` (1 = drop-frame count) |
| 4    | 6    | zero `0` |
| 4    | 5..4 | `tc_10fr` |
| 4    | 3..0 | `tc_1fr` |

* BCD digits, derived from SMPTE ST 12-1 time code.
* `tc_field_flag`: for interlaced pictures, 0 = first field, 1 = second
  field. At 50 Hz and above, the progressive frame number is
  `2 * frame + tc_field_flag` (frame:flag runs 0:0, 0:1, 1:0, 1:1, ...).
* The section may be omitted where CDPs are bound to video frames
  (note under Table 3 / 4.2), as in MCC, where every line has its own
  time code.

## 5. ccdata_section (section 5.4, Table 5) — 2 + 3*cc_count bytes

| Byte | Bits | Field |
|------|------|-------|
| 0    | 8    | `ccdata_id` = 0x72 |
| 1    | 7..5 | marker `111` |
| 1    | 4..0 | `cc_count` |
| then `cc_count` x 3 bytes | | `11111` marker, `cc_valid`, `cc_type`(2), `cc_data_1`, `cc_data_2` |

* Should normally be present.
* `cc_count` shall be the Table 3 value for the CDP's frame rate.
* `cc_valid` / `cc_type` / `cc_data_1` / `cc_data_2` are as defined in
  CEA-708 (see `708.md`, `cc_data()`).
* The 608 data shall come first, followed by the 708 data.
* The full Table 3 allocation is always present: if 608 or 708 data is
  absent, its space is still allocated and filled with null (0x00)
  data bytes.

## 6. ccsvcinfo_section (section 5.5, Table 6) — 2 + 7*svc_count bytes, optional

| Byte | Bits | Field |
|------|------|-------|
| 0    | 8    | `ccsvcinfo_id` = 0x73 |
| 1    | 7    | reserved `1` |
| 1    | 6    | `svc_info_start` |
| 1    | 5    | `svc_info_change` |
| 1    | 4    | `svc_info_complete` |
| 1    | 3..0 | `svc_count` (0..15) |
| then `svc_count` x 7 bytes: | | |
| +0   | 7    | reserved `1` |
| +0   | 6    | `csn_size` (1 = 5-bit number, 0 = 6-bit) |
| +0   | 5..0 | if `csn_size`=1: reserved `1` + 5-bit `caption_service_number`; else 6-bit `caption_service_number` |
| +1..+6 | 6x8 | `svc_data_byte_1..6`: one ATSC A/65 caption_service_descriptor loop entry (A/65 section 6.9.2, Table 6.26) |

* `caption_service_number` 0 = the line-21 (608) service; 1..31 / 1..63
  must match the service number inside `svc_data_byte_4` for a DTVCC
  service.
* The information for up to 15 services per CDP may be spread across a
  run of CDPs. `svc_info_start` marks the CDP that begins a complete
  set, `svc_info_complete` the one that ends it (both 1 if one CDP
  holds the full set). `svc_info_change` is 1 from the start of the
  first complete set whose content differs from the previous set.
* Header copies of these three bits must match.
* A terminated service must not appear in later sets; a changed
  service's new information appears from the first set flagged with
  `svc_info_change`.
* Informative (4, 4.3): over a programme every construct is expected
  to appear at least once, and a CDP stream "typically" carries both
  caption data and service information; PSIP generators build the
  ATSC caption_service_descriptor (PMT / EIT) from it. Not mandatory.

## 7. cdp_footer (section 5.6, Table 7) — 4 bytes, required

| Byte | Bits | Field |
|------|------|-------|
| 0    | 8    | `cdp_footer_id` = 0x74 |
| 1–2  | 16   | `cdp_ftr_sequence_cntr`: equal to `cdp_hdr_sequence_cntr` |
| 3    | 8    | `packet_checksum`: makes the 8-bit sum of every CDP byte, identifier through checksum, equal 0 mod 256 |

## 8. future_section (section 5.7, Table 8)

`future_section_id` (0x75..0xEF), `length` (remaining bytes), then
`length` data bytes. Placed just before the footer; receivers skip ids
they do not understand.

## 9. Encoder checklist

1. Header: 0x96 0x69, `cdp_length` = total CDP bytes, rate code from
   Table 3 in the high nibble with `1111` below, flags with bit 0 = 1.
2. Presence flags match the sections actually included; svc_info_* are
   0 unless a ccsvcinfo_section is present, and then equal its copies.
3. `caption_service_active` reflects whether the stream carries an
   active caption service (608 or 708).
4. `cc_count` and the 608 / 708 tuple split per frame follow Table 3
   exactly; 608 tuples first; unused slots null-filled.
5. Header and footer counters equal; +1 per CDP, wrapping at 65536.
6. `packet_checksum` zeroes the CDP sum mod 256.
